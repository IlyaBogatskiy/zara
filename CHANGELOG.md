## [Unreleased]

### Added
- 📈 **Утренняя сводка активности в админ-чат**: раз в сутки (`zara.activity-summary.cron`, по
  умолчанию 09:00) — отчёт «как живёт бот»: текущий охват (товары, чаты, подписки с разбивкой
  ждут/следят) и счётчики событий за сутки (появления, пропажи, ценовые, товар целиком). Счётчик
  `ActivityStats` наполняется в `UserNotifier` по мере отправки отчётов и обнуляется при выгрузке.
  В отличие от дайджеста WARN/ERROR, шлётся всегда — это сама сводка, а не сигнал о проблеме. Ровно
  «для понимания работы бота и сбора статистики».
- 🌐 **Вотчдог деградации API**: `ApiHealthTracker` считает на скользящем окне (по умолчанию 20
  запросов), как часто быстрый JSON-путь отдаёт данные, а как часто приходится откатываться в
  Selenium. Когда доля откатов превышает порог (`zara.api.degraded-threshold`, по умолчанию 0.5) —
  алерт в админ-чат (с троттлингом): ранний сигнал, что Akamai закручивает гайки и бот работает на
  медленном Selenium-пути, пока ещё технически жив. Одиночная транзиентная ошибка API порог не
  срывает — только устойчивая доля. `zara.api.degraded-window: 0` выключает вотчдог.
- 📵 **Алерт о недоставленных оповещениях**: если отчёт пользователю так и не ушёл — исключение при
  отправке, ошибка Telegram (например, бот заблокирован), или 429 после всех ретраев — `UserNotifier`
  шлёт в админ-чат «не удалось доставить оповещение в чат X: причина» (троттлинг под одним ключом,
  чтобы массовый сбой Telegram дал один алерт, а не по одному на чат). Раньше потерянное оповещение
  было видно только в логах.
- 🌀 **Уведомление о карантине флапа в админ-чат**: когда анти-флап помечает размер как мигающий и
  ставит его рестоки в карантин, в админ-чат уходит пинг ««товар» размер X мигает — рестоки в
  карантине на N тиков» (с троттлингом на пару товар+размер). Раньше карантин был виден только в
  логах; теперь оператор сразу знает, какой товар «прыгает».
- 🛠 **Админ-команды в самом боте (только для `admin-chat-id`)**: read-only статистика прямо из
  Telegram, без открытого HTTP-порта (`OperatorController` помечен «local only»). Единый listener
  остаётся один (у бота один поток обновлений), а разделение админ/пользователь сделано на уровне
  обработчика: `AdminCommandHandler.tryHandle` отвечает только для админ-чата и только на команды
  `/stats`-семейства, всё остальное (не тот чат, ссылка на товар, неизвестная команда) проваливается
  в обычный пользовательский поток — так что и обычные действия админа продолжают работать. Команды:
  `/admin` (справка), `/stats` (товары/чаты/подписки, разбивка по режимам), `/products`,
  `/product <ключ>` (кто и за какими размерами следит + последняя цена), `/chats`, `/chat <id>`
  (что отслеживает конкретный чат). Всё читается напрямую из `SubscriptionService`, ничего не меняет.
- 🛎 **Операционные алерты в админ-чат (watchdog / медленный тик / старт-стоп)**: три сигнала,
  которых не хватало, чтобы замечать проблемы без жалоб пользователей. (1) **Watchdog простоя** —
  планировщик помнит время последнего завершённого тика; если разрыв до текущего превышает
  `zara.monitor.stall-alert-ms` (по умолчанию 5 мин), возобновившийся тик шлёт админу «мониторинг
  простаивал X мин, изменения наличия пропущены» (в логе был провал 3ч35м без единого следа —
  теперь такой факт всплывёт). (2) **Медленный тик** — если тик длится дольше
  `zara.monitor.slow-tick-alert-ms` (по умолчанию 15 с), алерт (с троттлингом): почти всегда это
  синхронный Selenium-fallback, блокирующий однопоточный планировщик (в логе были тики по 5–79 с).
  (3) **Старт/стоп бота** (`AdminLifecycleNotifier`) — пинг «✅ запущен: N товаров, K чатов» после
  прогрева и «⏹ останавливаюсь» на shutdown; всплеск стартовых пингов = сигнал краш-лупа. Всё идёт
  через `AdminNotifier` (для событий добавлен `notice()` — без 6-часового троттла) и требует заданного
  `zara.admin-chat-id`.
- 📨 **Суточный дайджест WARN/ERROR в Telegram**: bounded in-memory appender (`LogDigestCollector`)
  копит все события уровня ≥ WARN по всем логгерам в течение дня (SQL DEBUG/TRACE в буфер не
  попадает — отсекается по уровню, поэтому дайджест крошечный и не утекают значения bound-параметров),
  а `@Scheduled`-джоб (`zara.log-digest.cron`, по умолчанию 23:55) раз в сутки шлёт их `.txt`-файлом
  в админ-чат (`zara.admin-chat-id`). **Без heartbeat**: в «чистый» день не отправляется ничего.
  Так проблемы, о которых не сообщил отдельный алерт (например, повторяющийся canary-mismatch по
  `p06318052` или откаты API→Selenium), всё равно попадают на глаза. Кольцевой буфер ограничен
  (`max-entries`, по умолчанию 5000; при переполнении отбрасывает старые и указывает их число в
  шапке). Настройки: `zara.log-digest.enabled/cron/zone/max-entries`.
- 🔍 **Трейс решений мониторинга в логах**: `MonitoringScheduler` теперь подробно логирует весь путь
  принятия решения по каждому товару за тик — что вернул скрейп (`raw`, цена, предыдущее
  подтверждённое состояние), как отработал дебаунс (удержание/коммит перехода), результат
  Selenium-подтверждения рестока, и **каждое оповещение с его причиной** (`ALERT SIZE_APPEARED /
  SIZE_SOLD_OUT / WHOLE_AVAILABLE / PRICE moved` — кому, по какому размеру, из какого перехода).
  Так по логам можно реконструировать, **почему и когда** пришло оповещение (в т.ч. разобрать
  ложное «размер пропал/появился»). Все строки помечены `MON [<productKey>]` для грепа; уровень
  INFO — переходы и оповещения (видно по умолчанию), DEBUG — полный дамп скрейпа и удержания
  дебаунса (включается `logging.level.com.ibdev.bot.zara.scheduler.MonitoringScheduler=debug`).
- 📋 **Полная размерная линейка в карточке**: скрейп теперь отдаёт **все** размеры с реальным
  наличием (не только отсутствующие), и пользователь может выбрать для отслеживания любой — даже тот,
  что уже в наличии. В пикере каждый размер помечен: 🟢 — в наличии, 🔴 — нет. Режим подписки
  выбирается автоматически по наличию на момент подписки: 🔴 → ждём рестока (`AWAIT_RESTOCK`),
  🟢 → следим за ценой и пропажей (`WATCH_IN_STOCK`). Так можно на одном товаре ждать один размер
  и одновременно следить за ценой другого. Дальше работают уже существующие механизмы оповещений.

### Changed
- 🔄 **Товар целиком (`*`) отслеживается в обе стороны**: раньше whole-подписка была
  однонаправленной и разовой — срабатывала при появлении товара и **сразу авто-отписывалась**,
  поэтому исчезновение размерной линейки целиком никто не замечал. Теперь `*` — постоянная и
  двунаправленная (симметрично per-size): при появлении шлём «✅ Товар появился» + размерную сетку
  (в наличии / отсутствующие) и **не отписываемся**; при полном исчезновении (все размеры OOS или
  страница «товар недоступен») — новое «❌ Товар снова полностью пропал» с вопросом «продолжить?»
  (кнопки **✅ Продолжить** / **❌ Остановить**). Оба события — по переходу, через дебаунс. Кнопка
  «📌 Отслеживать отсутствующие» остаётся как дополнительное действие (стандартная подписка на
  конкретные размеры), `*` при этом продолжает жить до явного «Остановить» или отписки через меню.
- 🔇 **SQL-логи снижены до `WARN`**: `org.hibernate.SQL` (был `debug`) и
  `org.hibernate.orm.jdbc.bind` (был `trace`) теперь на `WARN`. По разбору суточного лога это 99.8%
  объёма (стейтменты ~70%, значения bound-параметров ~25%, и последние утекали chat id / ключи
  товаров). Для локальной отладки запросов подними `org.hibernate.SQL` до `debug`.

### Fixed
- 🐤 **Ложная тревога канарейки на распроданном товаре**: `SelectorCanary` сравнивал Selenium и API
  по **присутствию ключа размера**, а не по стоку. Когда товар распродан целиком, Zara отдаёт
  страницу «товар недоступен» → Selenium схлопывается в единственный сентинел `{"*": false}`, а API
  всё ещё перечисляет каждый размер как `out_of_stock`. По сути они **согласны** («купить нечего»),
  но канарейка объявляла это расхождением и слала «размер X: есть в API, не найден Selenium-парсингом»
  по каждому размеру (реальный инцидент: `09598104`, дважды за 6 ч). Теперь сравнение идёт **по
  наличию**: алерт только когда API видит размеры в наличии, а Selenium — ноль (историческая тихая
  смерть мониторинга) либо сток по размеру реально расходится; полностью распроданный товар канарейку
  не будит. Плюс при настоящем расхождении сохраняется **дамп страницы** (`dumps/canary-mismatch-*`) —
  раньше на пути `{"*": false}` дамп не писался, и различить «распродажа» от «Akamai-челлендж» было
  нечем. Порядок в `checkSelectors` — API-first: нет API-базлайна → Selenium не поднимается зря.
- 🔁 **Спам «размер пропал ↔ появился» каждые ~30 сек**: burst-confirm (быстрый повторный скрейп
  через 3 с, чтобы подтвердить перемену в тот же тик) ускорял **обе** стороны — и рестока, и
  распродажи. Из-за этого кратковременный блип наличия у Zara (товар на пару секунд читается как
  OOS — его ловят и тик, и burst-скрейп в 3 с) коммитил ложную пропажу `SIZE_SOLD_OUT`, а следующий
  тик возвращал наличие и слал зеркальное `SIZE_APPEARED`. По логам — 8 сообщений за 7 минут по
  одной сумке (`16076710`), которая на деле стабильно в наличии. Дебаунс (2 подтверждения) это не
  фильтровал, потому что оба «подтверждения» происходили в окне 3 с, а не разнесённо между тиками.
  Теперь **burst-confirm ускоряет только ресток (OOS→в наличии), но не распродажу**: распродажа
  подтверждается только независимым кросс-тиковым наблюдением (2 скрейпа по ~30 с). Одиночный
  OOS-блип больше не коммитится → нет ни ложной пропажи, ни зеркального появления. Быстрое
  оповещение о реальном рестоке сохранено. (Остаточный зеркальный кейс — реально отсутствующий
  товар, мигающий «в наличии» пару секунд, — закрыт анти-флап кулдауном + карантином, см. ниже.)
- 🚦 **Анти-флап кулдаун + карантин** (`zara.monitor.anti-flap-cooldown-ticks`, в коде **0/выкл**,
  в `application.yaml` — **3**; `flap-quarantine-ticks`, по умолчанию 60): закрывает остаточный
  флап, который оставлял burst-confirm — реально отсутствующий товар, чей JSON-ответ Zara мигает
  «в наличии» дольше 3 с (окно burst-скрейпа), но короче тика. Burst повторно читал тот же залипший
  ответ CDN и коммитил ложный ресток, а следующий тик его откатывал → `SIZE_SOLD_OUT ↔ SIZE_APPEARED`
  по кругу (инцидент 2026-07-19 по куртке `03046090`, размер XL — 5 сообщений за ~12 минут при
  товаре, которого нет). Теперь: после любого флипа размер N тиков **не имеет права на burst**
  (`anti-flap-cooldown-ticks`) — его следующий флип должен быть подтверждён независимым кросс-тиком,
  а не повторным чтением того же края CDN; если противоположный флип случается **в пределах этого
  окна** (детект флапа), размер уходит в **карантин** (`flap-quarantine-ticks` ≈ 30 мин при периоде
  30 с), где его рестоки глушатся (откатываются, без оповещения). Итог: мигающий товар даёт **максимум
  одну ложную пару «появился/пропал», дальше тишина**; по истечении карантина настоящий ресток снова
  оповещается штатно. **Opt-in** (как `confirm-restock-via-selenium`), потому что карантин может
  приглушить и *настоящий* быстрый ресток; `anti-flap-cooldown-ticks: 0` выключает механизм целиком.
- 🔔 **«Товар пропал, но уведомление не пришло»**: раньше оповещение о пропаже (`SIZE_SOLD_OUT`)
  и о цене слалось только для размеров в режиме `WATCH_IN_STOCK`, а все размеры, на которые
  подписались пока их не было в наличии, — в режиме `AWAIT_RESTOCK` («ждём появления»). В нём бот
  сообщал о появлении, но молчал о последующей пропаже, пока пользователь вручную не нажмёт
  «Следить». По логам за 8 часов — 3 оповещения «появился» и 0 «пропал». Теперь **наличие
  (появился/пропал) уведомляется в обе стороны для любого отслеживаемого размера, независимо от
  режима**; режим управляет только **ценовыми** уведомлениями (opt-in по кнопке «Следить за ценой»).
  Побочно: если размер появляется и другой пропадает у одного товара в один тик, они схлопываются
  в одно сообщение.
- 🧭 **Роутинг меню подписок после рестарта**: список подписок кодировал каждый товар как
  эфемерный токен в сессии чата (`ChatSession.subsTokens`), а кнопки «открыть/отписаться/переключить
  размер» резолвили товар через этот токен. После рестарта бота или истечения сессии (30 мин) карта
  токенов пропадала → нажатие на подписку упиралось в «Контекст меню устарел» и возвращало к списку.
  Теперь все callback'и меню несут `productKey` (короткий `-p<digits>` id) прямо в данных —
  состояние в сессии не нужно, кнопки старых сообщений продолжают работать. `subsTokens`/
  `currentSubProductKey` удалены за ненадобностью.
- 🚫 **Ложные «размер появился в наличии»**: раньше уведомление уходило по одному замеру, поэтому
  залежавшийся `in_stock` от Akamai-кэша или клиренс-товар, снятый с продажи (на странице «НЕТ В
  НАЛИЧИИ / ПОХОЖИЕ ТОВАРЫ»), давал ложное оповещение. Теперь два эшелона защиты:
  - **Дебаунс переходов** (`zara.monitor.confirmations`, по умолчанию 2): изменение наличия должно
    подтвердиться на N замерах подряд, прежде чем закоммититься и уйти в уведомление. Симметрично
    гасит и ложные «пропал»/«цена». Restart-safe (в БД пишется подтверждённое состояние).
  - **Selenium-подтверждение рестока** (`zara.monitor.confirm-restock-via-selenium`, **по умолчанию
    off, opt-in**): перед отправкой «появился» переход перепроверяется DOM-путём, который читает
    реальную покупаемость (VIEW SIMILAR + отсутствие кнопки «в корзину»). Если Selenium уверенно
    говорит «недоступно» — уведомление не шлётся; при ошибке Selenium доверяем API. Один запрос на
    товар и только на тик с рестоком, для отслеживаемых размеров. ⚠️ Выключено по умолчанию, т.к.
    Selenium-скрейп идёт **синхронно в однопоточном шедулере** — может заблокировать тик на 10–120 с
    (особенно за нагруженным Selenium Grid) и, при дрейфе DOM-селекторов, тихо глушить реальные
    оповещения. Включать только при быстром и здоровом Selenium; штатный фильтр блипов — дебаунс.
- 🏷 **Пометка `low_on_stock`**: размер с малым остатком остаётся «в наличии», но в сообщении теперь
  приписка «⚠️ Мало осталось — могут разобрать быстро» (ожидания вместо разочарования).

### Changed
- ⚡ **Burst-confirm — быстрое подтверждение изменений** (`zara.monitor.burst-confirm`, по умолчанию
  on): вторая проверка дебаунса раньше ждала целый `period-ms` до следующего тика — это и была
  основная часть задержки. Теперь, если отслеживаемый размер после первого наблюдения ещё не
  подтверждён, недостающее наблюдение добирается **сразу** (быстрый повторный API-скрейп через
  `burst-confirm-delay-ms`, дефолт 3с), и реальное изменение подтверждается/уведомляется в том же
  тике (~секунды вместо ~периода). Ограничено бюджетом на тик (`burst-confirm-max-per-tick`, дефолт
  3); неудачный повторный скрейп откатывается к обычному межтиковому дебаунсу (не хуже, чем было).
  Компромисс: два чтения в секундах друг от друга — чуть менее независимы, чем при 30с-разрыве
  (могут повторить устаревший edge-кэш); межтиковый дебаунс остаётся бэкстопом. Сделано по TDD
  (сначала падающие тесты, потом код).
- ⏱ **Период мониторинга 60с → 30с** (`zara.monitor.period-ms`): по логам тик занимает ~1.4с на 9
  товаров, так что узкое место задержки — не производительность, а связка `period × confirmations`.
  При debounce=2 это давало задержку оповещений до ~2 мин; с 30с — до ~1 мин, анти-бликовая защита
  (2 подтверждения) сохранена, нагрузка на скрапинг остаётся лёгкой (~9×0.5с API на 30с).
- 🧪 **Покрытие жизненных циклов мониторинга тестами**: добавлен `stubProductSequence` (несколько
  тиков подряд) и набор тестов — появление→пропажа→появление и зеркальный цикл; 1/2/3 размера,
  появляющиеся/пропадающие вместе, схлопываются в один отчёт за тик; кейс L/XL (один появился +
  другой пропал в один тик); частичное изменение (в отчёте только изменившиеся размеры); несколько
  товаров с несколькими размерами → один отчёт на чат; несколько чатов на один товар. Эти условия
  невозможно надёжно воспроизвести на живой Zara — тесты стали спецификацией поведения.
- ⬆️ **Обновление зависимостей**: Spring Boot `4.0.6 → 4.1.0` (тянет за собой согласованный набор
  BOM-версий — Jackson, Logback, Hibernate, Caffeine `3.2.3→3.2.4`, PostgreSQL `42.7.10→42.7.13`,
  Testcontainers, H2, Lombok, сам Spring), Selenium `4.44.0 → 4.46.0` (+ образ
  `selenium/standalone-chrome` в docker-compose синхронно), pengrad telegram-bot-api `10.0.0 → 10.1.0`.
  springdoc `3.0.3` — уже актуален. Полный прогон (65 тестов, включая Testcontainers-контекст) — зелёный.
- 📨 **Один сводный отчёт вместо пачки сообщений**: все изменения по одному чату за тик
  (появления/пропажи размеров, изменения цены, «товар целиком») теперь собираются в **одно**
  сообщение, сгруппированное по товарам. При одновременных изменениях по многим подпискам это
  резко снижает число сообщений — а значит, и риск, что часть уведомлений «съест» rate-limit
  Telegram и они молча не дойдут. Кнопки действий подписаны размером/товаром; по нажатию
  показывается всплывающее подтверждение (`answerCallbackQuery`), и из отчёта убираются только
  кнопки этого пункта — остальные остаются.
- 🛡 **Доставка уведомлений теперь проверяется**: ответ Telegram больше не игнорируется —
  при `429` (rate-limit) отправка повторяется с учётом `retry_after`, прочие ошибки логируются.

### Планы

- 🔐 Защита операторского API (Spring Security / фильтр по IP) — обязательна перед выходом наружу.
- 🚀 Прод-профиль: `ddl-auto: validate`, SQL-логи на `INFO`, секреты только из окружения.
- 📊 Метрики (Micrometer/Prometheus): длительность тика, hit-rate кэша, доля фоллбеков на Selenium.
- 🌍 Локализация сообщений бота (ru/en/me/sr) — сейчас все тексты на русском.
- ⏱ Адаптивный период мониторинга: чаще для «горячих» товаров, реже ночью; jitter между товарами.
- 🧠 Различение статуса `back_soon` («скоро будет») от «нет в наличии» в уведомлениях.
- 🗜 Пул WebDriver / `AsyncLoadingCache` для карточек — если Selenium-фоллбек станет основным путём.
- 📈 История подписок как фича: статистика «сколько ждали размер», самые востребованные товары.

## [1.1.0] — 2026-06-29

### Added
- 💶 **Отслеживание цены во время распродаж**: каждый тик мониторинга, помимо наличия,
  считывает текущую цену товара (из того же JSON Zara — без второго запроса; Selenium-фоллбек
  парсит цену best-effort и не падает, если не нашёл). Цена хранится на товаре
  (`products.last_price_*`) и переживает рестарт. Карточка товара теперь показывает цену.
- 🔁 **Спросить «продолжать ли следить» после появления размера**: когда размер вернулся в
  наличие, бот больше не отписывается молча, а присылает кнопки **«✅ Да, следить за ценой и
  наличием» / «❌ Нет, остановить»**. «Да» переводит подписку в режим `WATCH_IN_STOCK`.
- 👀 **Режим наблюдения за товаром в наличии** (`subscriptions.mode` =
  `AWAIT_RESTOCK` / `WATCH_IN_STOCK`): в режиме `WATCH_IN_STOCK` бот уведомляет об изменении
  цены (вверх/вниз) и о том, что размер снова пропал; при пропадании симметрично спрашивает
  **«✅ Да, ждать появления» / «❌ Нет»**, возвращая подписку в `AWAIT_RESTOCK`.

### Changed
- Планировщик при появлении размера больше **не** делает авто-отписку — подписка ждёт
  решения пользователя (кнопки выше). Авто-отписка осталась только для режима «товар целиком».
- Живой эндпоинт операторского API `/api/availability` теперь возвращает наличие **и** цену
  (`ProductSnapshot`); путь карточек/мониторинга наполняет новые модели `ProductSnapshot` и `PriceInfo`.
- Smoke-тест `ZaraBotApplicationTests` переведён на **Testcontainers** (`@ServiceConnection`):
  поднимает свой одноразовый PostgreSQL, больше не требует внешней БД на `localhost:5432` —
  достаточно запущенного Docker. Теперь `mvnw clean install` проходит из коробки.

## [1.0.1] — 2026-06-10

### Added
- 🐳 **Docker Compose**: весь стек одной командой (`docker compose up -d --build`) —
  PostgreSQL + `selenium/standalone-chrome` + бот. Образ бота тонкий (JRE, без Chrome):
  Selenium-фоллбек ходит в контейнер браузера через новый параметр

### Changed
- Все зависимости подняты до актуальных стабильных версий: Spring Boot 4.0.2 → **4.0.6**
  (Spring Framework 7.0.7, Hibernate 7.2.12, Jackson 3.1.2), java-telegram-bot-api 9.3.0 → **10.0.0**,
  springdoc 3.0.0 → **3.0.3**, Selenium → **4.44.0** (через переопределение `selenium.version` Boot BOM).
  Spring Boot 4.1 пропущен сознательно — пока только RC.
- Версии библиотек вынесены в раздел `<properties>` pom.xml.
- **Пакеты реорганизованы по слоям** вместо технических паттернов: `telegram/` (UI-слой:

- Переименования: `ProductDetailsDTO` → **`ProductCard`**, `SizeDetailsDTO` → **`SizeInfo`**

- Сборка уведомлений мониторинга вынесена в **`UserNotifier`** — планировщик больше не знает
  ни про Telegram, ни про callback-константы UI.

  `formatAllSizes`, `fromSize`, неиспользуемые поля DTO.

## [1.0.0] — 2026-06-10

Первый стабильный релиз. Полная переработка прототипа: новая архитектура, нормализованная БД, быстрый HTTP-путь мониторинга, самодиагностика и тесты.

### Added
- **Быстрый путь мониторинга и карточек** через внутренний JSON-эндпоинт Zara (`products-details`): ~0.5 с вместо 10–30 с headless Chrome; ретрай при сетевых сбоях; выключатель `zara.api.enabled`.
- **Канарейка селекторов** (`SelectorCanary`): каждые 6 ч сверяет Selenium-парсинг с JSON API на живом товаре; расхождение или падение → алерт оператору.
- **Алерты оператору** (`AdminNotifier`) в Telegram (`zara.admin-chat-id`) с rate-limit 6 ч на тип проблемы.
- **Дампы страниц** (`PageDumper`): HTML + скриншот в `dumps/` при каждой поломке парсинга, с ротацией.
- **Кнопка «Отслеживать отсутствующие»**: когда товар появился целиком, но часть размеров ещё нет — мониторинг продолжается по подтверждению.
- **Операторский REST API + Swagger UI** (`/api/**`, `/swagger-ui.html`): ручной запуск тика и канарейки, проверка наличия, CRUD подписок, метрики кэша.
- **Причина изменения подписки** (`SubscriptionChangeReason`): `USER_ACTION` / `AUTO_AVAILABLE` фиксируется при каждой отписке; история подписок сохраняется (строки закрываются, не удаляются).
- **Восстановление после рестарта**: последнее известное состояние размеров персистится каждый тик (`last_known_in_stock`) и поднимается при старте — без потерянных и дублированных уведомлений.
- **Тесты**: жизненный цикл подписок на H2 (10 сценариев), логика переходов планировщика (11), Telegram-флоу (7), живой тест Zara API (4).
- Конфигурация через `ZaraProperties` (`zara.*`) и переменные окружения (`TELEGRAM_BOT_TOKEN`, `DB_*`, `ZARA_ADMIN_CHAT_ID`).
- README на четырёх языках (ru/en/me/sr), документация архитектуры в `docs/`.

### Changed
- **Архитектура переработана полностью** (см. `docs/CACHE_REDESIGN.md`): событийная шина (8 событий, 3 async-листенера) удалена; прямые синхронные вызовы; подписки пишутся в БД write-through.
- **Схема БД нормализована**: `products` (один на товар) + `subscriptions` (строка на чат×товар×размер, размер — сырая строка без enum-потерь); миграция с легаси-схемы автоматическая (`LegacyDataMigration`), старые таблицы остаются до ручного удаления.
- **Кэширование на Caffeine**: карточки товаров (`expireAfterWrite 6h`, коалесцирование конкурентных скрейпов), сессии диалогов (`expireAfterAccess 30m` — закрыта утечка).
- **Планировщик группирует проверки по товару**: один скрейп на товар за тик независимо от числа подписчиков; ошибки изолированы per-product; лог длительности тика.
- **Скрейпинг убран с потока Telegram-апдейтов** (`ScrapingExecutor`): бот отвечает всем пользователям, пока грузится чья-то карточка.
- Chrome работает без загрузки картинок; User-Agent и таймауты вынесены в конфиг.

### Fixed
- **Критический баг мониторинга**: проверка наличия читала атрибут `data-qa-action` с элемента `<li>` вместо кнопки размера — все размеры всегда считались отсутствующими, уведомления не приходили никогда.
- `return` вместо `continue` в цикле мониторинга — одна отсутствующая карточка обрывала весь проход.
- NPE на незнакомых ключах в кэшах (цепочки `get(chatId).get(...)` без проверок).
- Инвалидация одного чата стирала состояния мониторинга всех чатов.
- `findAllWithSizesByChatId` игнорировал параметр `chatId` и возвращал товары всех чатов.
- Поломка селекторов маскировалась под «всё распродано» — теперь это громкий `ZaraParsingException` с дампом страницы и алертом.

### Security
- Токен бота и креды БД переопределяются переменными окружения (дефолты в `application.yaml` — только для локальной разработки; токен следует ротировать).
