# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Telegram bot (`com.ibdev.bot.zara`) that monitors **Zara** product pages for size availability. A user sends a Zara product link; the bot scrapes the page with **Selenium/ChromeDriver**, lets the user subscribe to specific out-of-stock sizes (or the product "as a whole"), and a background scheduler re-checks subscriptions and pings the user when a size comes back in stock — then auto-unsubscribes that size.

Stack: Spring Boot 4.1.x, Java 21, Maven, Spring Data JPA + PostgreSQL, pengrad java-telegram-bot-api 10.x, Selenium (version overridden via the Boot BOM `selenium.version` property — keep it in sync with the `selenium/standalone-chrome` image tag in docker-compose), Caffeine, springdoc. Dependency versions live in the pom `<properties>` section. **All user-facing bot text is in Russian.**

## Commands

```bash
# Build
./mvnw clean package          # mvnw.cmd on Windows PowerShell

# Run the bot (needs PostgreSQL + a Telegram token — see Configuration)
./mvnw spring-boot:run

# Test
./mvnw test                                   # all tests
./mvnw test -Dtest=ZaraBotApplicationTests    # single test class
./mvnw test -Dtest=ClassName#methodName       # single test method
```

`ZaraBotApplicationTests` is a context-load smoke test that spins up its own throwaway PostgreSQL via **Testcontainers** (`@ServiceConnection`), so `./mvnw test` and `clean install` need a running **Docker** but no external DB. All other tests need neither Docker nor a DB.

## Runtime prerequisites

Two ways to run:

**Docker (everything included):** `cp .env.example .env`, fill in `TELEGRAM_BOT_TOKEN`, then `docker compose up -d --build`. Stack: Postgres + `selenium/standalone-chrome` (the bot image has no browser; the Selenium fallback uses `RemoteWebDriver` via `ZARA_DRIVER_REMOTE_URL`) + the bot. All ports are bound to 127.0.0.1: 8100 (operator API/Swagger), 4444 (Grid console), 7900 (noVNC — watch the browser live), 5432 (Postgres). Parsing dumps land in `./dumps` on the host.

**Bare metal:**
- **PostgreSQL** at `jdbc:postgresql://localhost:5432/zara_bot` (user `zara`; overridable via `DB_URL`/`DB_USERNAME`/`DB_PASSWORD`). `ddl-auto: update` auto-creates the schema.
- **Google Chrome** on the host — Selenium drives a real headless Chrome (`--headless=new`, see `WebDriverConfig`); `zara.driver.remote-url` blank means local ChromeDriver.
- A **Telegram bot token** (`TELEGRAM_BOT_TOKEN` env or `telegram.token` in `application.yaml`). Long-polling via `setUpdatesListener` starts automatically; no webhook/public URL needed.

## Architecture

Redesigned 2026-06 (see `docs/CACHE_REDESIGN.md` for rationale). Direct synchronous calls top-to-bottom — **no event bus**. The flow: Telegram update → card from Caffeine cache (scrape on miss) → subscription written through to Postgres → scheduler polls per *product*.

### Layers (packages restructured 2026-06: by layer, not by technical pattern)
- `telegram/` — the whole Telegram UI layer: `ZaraTelegramListener` (text messages, inline-keyboard callbacks, the "pick sizes → confirm" flow — the picker lists the **full lineup** with 🟢/🔴 markers so any size is trackable, and `subscribe` picks the mode from each size's availability — subscriptions menu whose callbacks are **stateless**: `SUB_OPEN:`/`SUB_ALL:` carry the `productKey`, `SUB_TOGGLE:` carries `productKey:size`, so buttons keep working after a restart / session eviction — never resolve a menu action via per-session state), `ChatSession`+`SessionCache` (per-chat dialog state, **Caffeine** `expireAfterAccess 30min`), `ScrapingExecutor` (fixed pool of 2 that keeps card loads off the updates thread). **Admin commands (2026-07):** there is one physical `UpdatesListener` (one bot = one update stream), so admin/user separation is by *handler*, not by listener — `handleMessage` first calls `AdminCommandHandler.tryHandle(chatId, text)`, which returns a reply **only** for the `zara.admin-chat-id` chat and a recognized `/stats`-family verb (`/admin`, `/stats`, `/products`, `/product <key>`, `/chats`, `/chat <id>`); anything else (a non-admin chat, a product link, an unknown command) returns empty and falls through to the normal user flow, so the admin's own normal usage still works. These are **read-only** stats read straight from `SubscriptionService` — the same data the OperatorController serves, but gated by the admin chat instead of an open HTTP port.
- `client/` — everything that talks to Zara: `ZaraApiClient` (Zara's own `products-details` JSON endpoint, ~0.5 s, used first; needs the `v1` query param from the user's link as the color productId, HTTP/1.1 + browser headers to pass Akamai), `ZaraPageClient` (Selenium fallback; throws `ZaraParsingException` + `PageDumper` dump on unrecognized DOM), `WebDriverFactory`, and the scrape-result model: `ProductCard` (carries a `PriceInfo` and, since 2026-07, the **full size lineup** — `SizeInfo` per size with real `sizeAvailability`, not just OOS), `SizeInfo`, `ClothingSizes`, plus `ProductSnapshot` (the monitoring tick's combined `{sizes, price, lowStockSizes}` — `lowStockSizes` holds the `low_on_stock` sizes, filled by the API path, empty from Selenium) and `PriceInfo` (minor-units amount + currency + fraction digits). Price comes free from the same JSON; the Selenium path parses it best-effort and returns `null` on a miss (never throws — price is non-critical).
- `cache/ProductCardCache` — **Caffeine** (`maximumSize 5000`, `expireAfterWrite 6h`), key = `productKey` only (one card per product, not per chat). `getOrLoad(productKey, link)` scrapes on miss; Caffeine coalesces concurrent loads of the same key into one scrape.
- `service/subscription/SubscriptionService` — the domain core, deliberately **not** a cache (losing an entry would silently stop monitoring). Writes through to Postgres synchronously (`@Transactional`, repositories directly), then updates three in-memory indexes: `byChat` (chatId → productKey → **size→mode**, where mode is `SubscriptionMode`), `byProduct` (productKey → chatIds, the reverse index), and `productRefs` (productKey → link+name, so the scheduler survives card-cache eviction). The scheduler iterates `getActiveWatches(productKey)` → flat `List<Watch(chatId, size, mode)>`. `subscribe` sets each size's initial mode from the card's availability (in-stock → `WATCH_IN_STOCK` + `lastKnownInStock=true`, OOS → `AWAIT_RESTOCK`); `watchInStock`/`awaitRestock` flip it later (DB + index). Also owns `recordCheck` (persists last-known availability each tick), `recordCheck`'s price twin `recordPrice` (persists the last price on the product row) + `loadLastKnownPrices`, and the startup `warmUp` that rebuilds indexes from DB.
- `service/page/PageService` — API-first orchestration over the two `client/` backends; falls back to Selenium when the API returns nothing/403 (toggle: `zara.api.enabled`). `ApiHealthTracker` records each API attempt (served vs fell-back) over a sliding window (`zara.api.degraded-window`) and alerts the admin (throttled) when the fallback rate crosses `zara.api.degraded-threshold` — an early warning that Akamai is tightening and the bot is limping on the slow Selenium path; a single transient error never trips it.
- `scheduler/MonitoringScheduler` — `@Scheduled(fixedDelay = zara.monitor.period-ms)`. Iterates `SubscriptionService.activeProductKeys()` — **one scrape per product per tick regardless of subscriber count** — compares against its private `lastKnown` (size availability, absent = "was out of stock") and `lastKnownPrice` state. Rather than sending a message per change, it **accumulates `NotifyEvent`s per chat across the whole tick** into a `Map<chatId, List<NotifyEvent>>`, then flushes **one consolidated report per chat** via `UserNotifier.sendReport` (so a burst of simultaneous changes is one Telegram message, not ten — far fewer dropped by rate limits). **Availability is notified in both directions for every tracked size regardless of mode** (2026-07): out→in → `SizeAppeared` (**Yes/No keep-watching** buttons; no auto-unsubscribe — waits for the user), in→out → `SizeSoldOut` (**Yes/No keep-waiting** buttons). The `SubscriptionMode` only gates the extra **price** alerts: a price move on a product with any `WATCH_IN_STOCK` watcher → `PriceMoved` event (informational, no buttons) to those chats — price-watching is the opt-in the "keep watching" button grants. *(Before 2026-07 sold-out only fired for `WATCH_IN_STOCK` sizes, so an `AWAIT_RESTOCK` size that appeared then sold out went silent unless the user tapped "Следить" — the #1 "it disappeared but no notification" cause.)* The only remaining auto-unsubscribe is the WHOLE-product branch. Errors are isolated per product **and** per chat-report. Knows nothing about Telegram (events carry only `productKey`/name/link/sizes/price). **False-positive guards (2026-07):** `lastKnown` holds the *confirmed* (debounced) state, not the raw last reading. Each tick the raw scrape is folded through `debounce()` — a change commits only after `zara.monitor.confirmations` (default 2) consecutive agreeing observations (in-memory `pendingFlips` counter; comparison is fuzzy because a restart seeds `lastKnown` from subscribed labels, not raw scrape labels). A just-committed OOS→in-stock flip for a *watched* size **can optionally** be cross-checked by `confirmRestockViaSelenium` (`zara.monitor.confirm-restock-via-selenium`, **default OFF/opt-in** since 2026-07, only when `zara.api.enabled`): it runs `PageService.checkViaSelenium` once and, if the DOM says the size/product is not actually buyable, reverts the flip so no false "appeared" is sent (a Selenium *error* trusts the API; a Selenium *contradiction* wins). **Why opt-in:** this Selenium scrape runs *synchronously on the single-threaded scheduler* — it can block the whole tick for 10–120 s (worse behind a contended Selenium Grid) and, if the DOM path drifts, silently suppress real alerts and re-fire every ~2 ticks. The debounce is the always-on guard; enable this only with a fast, healthy Selenium. **Burst-confirm (2026-07, `zara.monitor.burst-confirm`, default ON):** the debounce's second observation normally waits a full `period-ms` for the next tick — that's the bulk of the notification latency. When a *watched* size is still short of confirmation on a pending **restock** (OOS→in-stock) after the first observation, `burstConfirmIfNeeded` fetches the missing observation *immediately* (a fast API re-scrape after `burst-confirm-delay-ms`, default 3 s) via `foldObservation`, so a real restock confirms and notifies within the same tick (~seconds instead of ~a period). Bounded by `burst-confirm-max-per-tick` (default 3); a failed/empty re-scrape degrades to the normal cross-tick debounce. **Burst accelerates restocks only — never sell-outs (2026-07):** `foldObservation` is passed `burst=true` on the re-scrape and refuses to advance an in-stock→OOS flip, and `hasUnconfirmedWatchedChange` only fires the re-scrape for a pending in-stock flip. A sell-out always waits for the independent cross-tick observation. This closes a spam bug where a seconds-long OOS blip — caught by *both* the tick scrape and the 3 s burst re-scrape — committed a false `SizeSoldOut`, immediately mirrored by a false `SizeAppeared` when the next tick reverted (`SOLD_OUT`↔`APPEARED` every ~30 s). Trade-off: the two reads are seconds apart, so slightly less independent than the 30 s cross-tick gap (may echo a stale CDN edge) — the cross-tick debounce stays as the backstop. **Anti-flap cooldown + quarantine (2026-07, `zara.monitor.anti-flap-cooldown-ticks`, default 0/OFF in code, set to 3 in `application.yaml`; `flap-quarantine-ticks`, default 60):** the residual the burst trade-off leaves — a genuinely-OOS product whose API reading flickers *in-stock* for a few seconds (longer than the 3 s burst gap but shorter than a period), so the burst re-scrape echoes the same stale CDN edge and commits a false restock, which the next tick reverts — `SOLD_OUT`↔`APPEARED` oscillating (the exact incident in the 2026-07-19 log for `03046090` XL). The scheduler reasons in a monotonic `tick` counter (≈ periods): once a size commits a flip, `burstSuppressed` bars it from burst-confirm for `anti-flap-cooldown-ticks` ticks — its next flip must earn the independent cross-tick debounce, not a same-edge re-scrape. `recordFlips` detects a **flap** (an opposite flip committed within that cooldown window) and quarantines the size (`FlipRecord.quarantinedUntilTick = tick + flap-quarantine-ticks`); while quarantined, `suppressQuarantinedRestocks` reverts any committed restock back to OOS and drops it from `appeared` (so no false appeared, and no mirroring sold-out next tick since the state never left OOS). Net: a flickering product yields **at most one false appeared/sold-out pair, then goes quiet** until the quarantine elapses (~30 min), after which a genuine restock alerts normally again. **Opt-in like `confirm-restock-via-selenium`** because a quarantine can also mute a *genuine* rapid restock; `anti-flap-cooldown-ticks: 0` disables the whole machinery. All state (`flipHistory`, `tick`) is in-memory — a restart re-accumulates. When a flap is detected `recordFlips` also pings the admin chat (`AdminNotifier`, throttled per product+size) so the operator sees *which* product is flickering, not just silence. `low_on_stock` sizes stay in-stock but ride along in `ProductSnapshot.lowStockSizes` → `SizeAppeared.lowStock` → a "⚠️ Мало осталось" line. **Observability:** the whole decision chain is logged with a `MON [<productKey>]` prefix — INFO for debounce commits **and holds** (a size seen changed but not yet confirmed — the counterpart to a commit, so the debounce *filtering* a blip is visible without DEBUG; low-volume, only on an actual pending disagreement), Selenium confirm/reject, and every alert *with its cause* (`ALERT SIZE_SOLD_OUT '<size>' → chat <id>` etc.); DEBUG for the raw per-tick scrape dump (enable via `logging.level.com.ibdev.bot.zara.scheduler.MonitoringScheduler=debug`). This is the first place to look when a notification seems wrong — grep `MON` to reconstruct why/when it fired. **Watchdog + slow-tick admin alerts (2026-07):** the scheduler tracks `lastTickCompletedAt`; the resuming tick alerts the admin chat (`AdminNotifier`) when the gap since the previous tick exceeds `zara.monitor.stall-alert-ms` (default 300 s) — a monitoring outage window (host suspend / container pause) during which stock changes were missed, detected on resume because a full freeze suspends every thread. And a tick that runs longer than `zara.monitor.slow-tick-alert-ms` (default 15 s) alerts (throttled) — almost always a synchronous Selenium fallback blocking the single-threaded scheduler. Both are 0-to-disable.
- `scheduler/SelectorCanary` — every 6 h (`zara.canary.*`) runs the Selenium path on one live monitored product and cross-checks the result against the JSON API. Disagreement or a parse failure → `AdminNotifier` alert. This exists because a broken selector used to look exactly like "everything out of stock" — notifications just stopped.
- `notify/` — all outgoing Telegram messages outside the dialog flow: `NotifyEvent` (sealed model of one monitoring change — `SizeAppeared`/`SizeSoldOut`/`PriceMoved`/`WholeAvailable`), `UserNotifier` (`sendReport(chatId, events)` folds a chat's whole-tick events into one report grouped by product, appends labelled action-button rows per actionable event, and **checks the send response — retrying on HTTP 429 with `retry_after`**, escalating a *terminal* delivery failure (thrown send, a non-429 Telegram error, or 429 after all retries) to `AdminNotifier` under one throttled `delivery-failed` key so a dropped report isn't a silent loss, and tallying each sent event into `ActivityStats`; owns the callback constants that `telegram/` handles — `CB_WHOLE_KEEP_PREFIX`, plus `CB_SIZE_WATCH_PREFIX`/`CB_SIZE_AWAIT_PREFIX`/`CB_SIZE_STOP_PREFIX`, each carrying a `productKey:size` payload) and `AdminNotifier` (operator alerts: always ERROR-logs, additionally messages `zara.admin-chat-id` if set, rate-limited to one per 6 h per problem key). **Daily WARN/ERROR digest (2026-07):** `LogDigestCollector` is a bounded in-memory Logback appender that attaches to the root logger on startup and captures every event at level ≥ WARN across all loggers (the SQL DEBUG/TRACE flood never enters it — dropped by level — so it stays tiny and leaks no bound-parameter values); it's a fixed-capacity ring (drops oldest, counts drops). `DailyLogDigestReporter` runs a `@Scheduled` cron (`zara.log-digest.cron`, default 23:55) that drains the buffer and, **only when non-empty (no heartbeat)**, ships it as a `.txt` via `SendDocument` to `zara.admin-chat-id` — surfacing problems no dedicated alert reported. `render(...)` is pure (clock/zone injected) for testing; no admin chat → logged as produced-but-undeliverable. Toggle `zara.log-digest.enabled`. `AdminNotifier.notice(msg)` is the un-throttled sibling of `alert(key,msg)` for one-off lifecycle events; `AdminLifecycleNotifier` uses it to ping the admin chat on startup (`ApplicationReadyEvent`, `@Order(20)` — after warm-up, so it reports restored product/chat counts; a burst of these is the crash-loop signal) and on shutdown (`ContextClosedEvent`). **Daily activity summary (2026-07):** `ActivityStats` tallies user-facing events (appeared/sold-out/price/whole) as `UserNotifier` sends them; `DailyActivitySummaryReporter` drains them once a day (`zara.activity-summary.cron`, default 09:00) and posts a "how the bot lived" report — monitoring footprint (products/chats/size subscriptions, mode split) plus the day's counts — to the admin chat. **Always sent** (it is the report, not an alert — the ops-stats counterpart to the WARN/ERROR digest). Because report buttons live in one shared message, `ZaraTelegramListener` resolves an action-button tap with a **toast** (`answerCallbackQuery`) and `filterOutButtons` — dropping only that item's buttons from the report keyboard (`EditMessageReplyMarkup`) instead of rewriting the whole message.
- `web/OperatorController` — testing/diagnostics REST API under `/api` (Swagger UI at `/swagger-ui.html`, springdoc): live availability check, card load (`fresh=true` bypasses cache), subscriptions CRUD, **manual triggers for the monitoring tick and the canary**, Caffeine cache stats. **No auth — local use only, never expose publicly.** For remote inspection, the read-only subset (stats, who-monitors-what) is exposed through the Telegram bot's admin commands instead — gated by `zara.admin-chat-id`, no open port (see `telegram/AdminCommandHandler`).
- `util/` — `ProductLinks.extractProductId` and `Sizes.equalsSize` (pure static helpers).
- `storage/` — normalized schema (2026-06): `products` (key = `product_key`; name, link, `last_scraped_at`, plus `last_price_amount`/`last_price_currency`/`last_price_fraction_digits` — the restart-safe price baseline — scrape facts, one row per product, **no size rows**: the size lineup is always taken fresh from a scrape) and `subscriptions` (one row per `(chat_id, product_key, size_label)`; `size_label` is the raw normalized string — no enum mapping; `mode` is `SubscriptionMode` (`AWAIT_RESTOCK`/`WATCH_IN_STOCK`); `last_known_in_stock` + `last_checked_at` written by the scheduler each tick; unsubscribe **closes** the row via `closed_at`+`close_reason` (`SubscriptionChangeReason`) instead of deleting, re-subscribe reopens it — and resets `mode` to `AWAIT_RESTOCK`).
- Startup sequence on `ApplicationReadyEvent`, ordered: `@Order(1)` `storage/LegacyDataMigration` (one-shot copy from the old `product_details`/`size_details` tables if `subscriptions` is empty; old tables are left for manual drop) → `@Order(2)` `SubscriptionService.warmUp` (rebuild indexes) → `@Order(3)` `MonitoringScheduler.seedLastKnown` (resume monitoring from persisted availability **and** price state — no duplicate notifications after a restart). The card cache is *not* warmed: cards reload on demand via `getOrLoad`.

### Conventions worth knowing
- **Workflow: test-first (TDD) for behaviour.** For any bug fix or behaviour change in the domain/logic layer — `scheduler/MonitoringScheduler`, `service/subscription/SubscriptionService`, `notify/UserNotifier`, Telegram callback routing — follow red→green→refactor with an explicit design step: (1) agree on the expected behaviour in plain terms (often a product decision here — e.g. "what happens when an AWAIT size sells out?"); (2) write the test(s) that encode it and **watch them fail for the right reason (red)** — a test written after the code and green on the first run doesn't prove it checks anything; (3) implement to green; (4) run the full suite + verify. Mock-driven tests are the *only* practical way to reproduce Zara's stock/price/size conditions, so the tests are the behaviour **spec**, not just regression guards. Scope notes: parsing against the live/external Zara (`ZaraApiClient`/`ZaraPageClient`) is covered by live or **fixture** tests (saved real JSON/HTML), not pure TDD; infra/timing/external failures (Selenium hangs, Telegram 429, Akamai) are caught by observability/timeouts/fail-open, not unit tests; trivial mechanical changes (config default, rename, docs) don't need a red-first test (a guard test is still welcome).
- **Comments: block comments above methods/types only — no inline `//` comments.** Explain *why* in a `/** … */` (or `/* … */`) block directly above the method, class, or field it documents. Do not add single-line `//` comments inside method bodies (in either main or test code); if a step needs justifying, either lift that rationale into the method's block comment or make the code self-explanatory (rename, extract a well-named helper). URLs and existing YAML `#` config comments are not affected.
- **`productKey`** is extracted from the URL (the `-p<digits>` segment) by `util/ProductLinks.extractProductId`. It is the primary correlation key across all caches and the DB. On a malformed URL it falls back to returning the raw path/link, so a bad link silently becomes a junk key.
- **The "whole product" sentinel**: `ClothingSizes.WHOLE` = `"*"`. Subscribing to `*` means "notify when the product (any size) becomes available," used when Zara shows "VIEW SIMILAR" / hides the size list. The scheduler branches on this in `notifyWholeProductIfAvailable`; when the product comes back with some sizes still missing, the notification offers a `WHOLE_KEEP:` inline button that re-reads the card (cache invalidated first) and subscribes the chat to the still-missing sizes.
- **Size matching** is fuzzy: `util/Sizes.equalsSize` treats `"EU40"` and `"40"` as equal; sizes are normalized (whitespace-stripped, uppercased) in several places. `ClothingSizes` survives mainly for the `WHOLE` sentinel and the legacy-migration enum mapping; `subscriptions.size_label` stores raw strings.
- **Availability polarity — verify which applies before touching availability logic:**
  - The **card DTO** (`loadProductCard` in both clients, since 2026-07) carries the **full size lineup** — every size with its real `sizeAvailability` (`true` = in stock). The Telegram picker shows all sizes (🟢 in stock / 🔴 out of stock) and the user can track any of them; `SubscriptionService.subscribe` then sets each size's mode by its current availability (in-stock → `WATCH_IN_STOCK`, OOS → `AWAIT_RESTOCK`). `outOfStockSizes()` still filters to the OOS ones (used by the whole-product "keep monitoring missing" flow); `isProductUnavailable()` still keys off the WHOLE `"*"` sentinel that only the Selenium "product unavailable" page emits. *(Historical note: the card DTO used to contain **only** out-of-stock sizes — consumers negated. That's gone.)*
  - The **live monitoring** path (`checkSizesAvailability` in both clients) and the DB column `subscriptions.last_known_in_stock` use direct polarity: `true` = in-stock. `MonitoringScheduler` treats a `false→true` transition as "appeared in stock."
- `ChatRegistry` only remembers the last-seen chatId (an `AtomicLong`); it is not a real multi-user registry and `getOrZero()` has no current consumer.
- **Availability values.** API path: `sizes[].availability` — `in_stock`/`low_on_stock` count as in-stock (`ZaraApiClient.IN_STOCK_VALUES`; `low_on_stock` also recorded in `lowStockSizes`); anything else (`out_of_stock`, `back_soon`, `coming_soon`, missing) is out-of-stock. Selenium path: the size button's `data-qa-action` must contain `in-stock` **and** the button be enabled/not `aria-disabled`. The reliable "whole product unavailable" signal only the DOM has is `isProductUnavailable()` (VIEW SIMILAR present + add-to-cart absent) — this is what the restock Selenium confirmation leans on.

## Performance & concurrency model (important before changing scraping)

- **Both paths are HTTP-first** (`zara.api.enabled`, default true): availability checks *and* card loading try the ~0.5 s JSON GET before falling back to Selenium. When Selenium does run, one ChromeDriver is created and `quit()` per call — there is no driver pool.
- **Card loading runs off the Telegram thread**: `handleMessage` replies "⏳" immediately and hands the load to `ScrapingExecutor` (fixed pool of 2 — a deliberate cap on concurrent Chrome instances). The updates listener thread never blocks on scraping.
- **The JSON endpoint is unofficial** — Akamai-fronted. It rejected JDK HttpClient defaults (HTTP/2 fingerprint → 403); the working config is HTTP/1.1 + browser-like headers in `ZaraApiConfig`. If Zara tightens this, the Selenium fallback keeps the bot alive (just slower). `ZaraApiClientTest` hits the live API (needs network, no Postgres/Chrome) — run it to verify the endpoint still works.
- **Selenium is not thread-safe, but each call gets its own driver**, so the scheduler thread and `ScrapingExecutor` threads scraping concurrently is safe in isolation — the cost is resource contention (multiple Chrome processes), not data races. Caffeine coalesces concurrent loads of the same product into one scrape.
- Config knobs live in `ZaraProperties` (`zara.*` in `application.yaml`): `user-agent` (shared by Selenium and HTTP paths), `api.enabled`, `driver.wait-seconds`, `monitor.period-ms`, `monitor.confirmations` (debounce, default 2), `monitor.confirm-restock-via-selenium` (default **false** — opt-in; blocks the scheduler tick, see MonitoringScheduler notes), `monitor.burst-confirm` (default **true**), `monitor.burst-confirm-delay-ms` (default 3000), `monitor.burst-confirm-max-per-tick` (default 3), `monitor.anti-flap-cooldown-ticks` (default **0** in code/opt-in, **3** in `application.yaml`), `monitor.flap-quarantine-ticks` (default 60), `monitor.stall-alert-ms` (default 300000, outage watchdog)/`monitor.slow-tick-alert-ms` (default 15000), `log-digest.enabled`/`.cron` (default 23:55)/`.zone`/`.max-entries` (daily WARN/ERROR digest to the admin chat), `activity-summary.enabled`/`.cron` (default 09:00)/`.zone` (daily activity summary), `api.degraded-window` (default 20)/`api.degraded-threshold` (default 0.5, API-degradation watchdog). Still hardcoded: CSS selectors (`ZaraPageClient`), Caffeine sizes/TTLs (`ProductCardCache`, `SessionCache`), `ScrapingExecutor` pool size.

## Known caveats

- **Subscriptions write through to Postgres synchronously** (`SubscriptionService` → `ProductDetailsService`, `@Transactional`): DB first, then in-memory indexes. Keep that order when extending — it's what guarantees the indexes never claim a subscription the DB doesn't have.
- `SubscriptionService` indexes must stay consistent with each other (`byChat`, `byProduct`, `productRefs`); mutate them only through the existing `index`/`dropChatFromProduct` helpers.
- When reading cache maps for possibly-unknown keys, guard the outer `get` (`getOrDefault(..., Map.of())` / null-check) — several NPEs of this class were fixed in 2026-06; keep the pattern.
- **`ZaraPageClient` must fail loudly, not lie.** When the DOM is unrecognized (no size rows after the popup, label/button selectors miss, add-to-cart never appears) it throws `ZaraParsingException` — never return "all out of stock". The only legitimate silent `{"*": false}` is the real "product unavailable" page (VIEW SIMILAR present, add-to-cart absent). Historical bug to not reintroduce: `checkSizesAvailability` once passed the `<li>` (not the size `<button>`) to `isInStock`, so `data-qa-action` was always null and *every* size read as out-of-stock — monitoring silently never fired.
- On every `ZaraParsingException`, `PageDumper` writes the page HTML + screenshot to `dumps/` (gitignored, rotated to ~20 pairs) — start there when debugging selector breakage. Chrome runs with images disabled (`--blink-settings=imagesEnabled=false`), so screenshots show placeholders.
- The API path retries once (300 ms pause) on transient HTTP failures before surfacing the error to the Selenium fallback.
- See `docs/IMPROVEMENTS.md` for the prioritized backlog of remaining improvements (async scraping, driver pooling, selector canary, DB normalization, etc.) and `docs/CACHE_REDESIGN.md` for the architecture rationale.

## Configuration & security notes

- **Secrets are committed in plaintext** in `application.yaml`: a live-looking Telegram bot token and the Postgres credentials. Rotate the token and externalize both (env vars / Spring config import) before any real deployment.
- `spring.jpa.hibernate.ddl-auto: update` auto-mutates the schema on startup — fine for dev, unsafe for prod (use `validate`/`none`).
- SQL logging is at `DEBUG`/`TRACE` (logs every statement and bound parameter) — very verbose and leaks data values; lower it for prod.
- Caffeine is used **directly** (`ProductCardCache`, `SessionCache`), not via the Spring Cache abstraction — no `@EnableCaching`/`@Cacheable` anywhere, by design (see `docs/CACHE_REDESIGN.md` §4.5).
- There is **no WebDriverManager dependency** — `new ChromeDriver(...)` relies on a system-installed Chrome + a chromedriver discoverable on PATH (or via Selenium Manager).
